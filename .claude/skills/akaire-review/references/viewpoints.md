# 赤入れの観点 (共通)

このファイルは、このブログの記事を AI が赤入れ (校閲) するときの **観点の唯一の置き場所** である。
akaire (tool/akaire、`claude -p` で起動) と GitHub Actions 上の @claude (.claude/skills/akaire-review/SKILL.md) の
両方がここを読む。出力の仕方 (.akaire.json への追記か、PR のインラインコメントか) は各々の側で定めるので、
ここには「何を見るか・何を指摘しないか・どう書くか」だけを書く。

観点を足したい・直したいときはこのファイルだけを編集する。

## 0. 役割と禁則

- AI の役割は雑誌編集でいう「赤入れ・鉛筆入れ」。文章を書くのは筆者であり、AI は修正指示を伝えるにとどめる
- **原稿本文 (.md) は一切書き換えない**。直すのは筆者の仕事
- 改善案は「こう直したらどうか」という指摘の形で伝える。書き直した文章を丸ごと提示しない。
  代案を示す場合も、筆者の語彙と文体を尊重した方向性の提示にとどめる
- 既存の指摘 (見送り = dismissed、対応済み = resolved を含む) を蒸し返さない。
  ただし対応後の文に新たな問題があれば、それは新しい指摘として出してよい
- 同じ趣旨の指摘を重複して出さない
- 1 指摘 1 論点

## 1. 文の成立 (最優先、kind "red")

文体・構成とは別軸で、**一文一文が文として成立しているか** を毎回必ず検査する。
口語崩し (2 章) はこのブログの味だが、こちらは味ではなく単なる破綻なので遠慮なく指摘する。

- **主述の対応**: 文の途中で主語がすり替わっていないか。述語がちゃんと着地しているか
  (例: 「〜する必要があるというのは、間違いなくある」のような「あるというのは、ある」型の重なり)
- **係り受け**: 「〜には」「〜としては」などの係りが、受けの述語まで届いているか
- **助詞**: 「は」の二連続による主題の競合、「を」であるべき箇所が「は」になっている、など
- **語の関係の不成立**: 「言葉から発せられた文言」のように、修飾関係が意味として成り立っていない表現
- **時制の噛み合わせ**: 「いま思えば〜と思っていた」のように、一文の中で判断の時点が食い違っていないか
- **譲歩・否定の二重化**: 「〜としても、それでも〜」「〜ないわけではなくはない」のような重なり
- **主語の欠落**: 節の冒頭で、直前が見出しなのに前文を受けたつもりの文になっていないか

音声入力由来の原稿では「しゃべっている間に述語の着地点を忘れる」パターンが頻出するため、特に重点的に見る。

## 2. 文体 (指摘しないもの)

このブログの記事は **だ・である調 + 口語崩し** で書かれている。ですます調は使わない
(ですます調は 2017 年頃のイベントレポート群のみで、近年の記事はすべてである調)。

- 基調は「〜である」「〜なのである」「〜かもしれない」「〜気がする」
- 口語の割り込みや自問 (「やめらんねぇ」「休むの下手か？」)、体言止めの相槌 (「気付き。」「超普通。」) はこのブログの味。
  「話し言葉だから」という理由で機械的に指摘しない
- 「で、」「ということで」「まあ」「なんだけど」「でもって」「あと」などの話し言葉の接続詞は現役。除去を提案しない
- 「？」「！」も普通に使う
- 文体まわりの指摘は「ですます調に直す」方向ではなく、である調・過去記事の声との一貫性を基準にする
- 言い回しの好みの範囲 (「発売する」vs「発売される」など) は、指摘するなら「好みの範囲」と添える

## 3. 構成・読みやすさ (kind "pencil")

差分・通しのどちらでも見る。

- 段落や節をまたいだ**内容の重複** (同じ説明が二度出ている)
- 一文が長すぎて読者が息切れする箇所。同じ語句が一文の中で二度出ている箇所
- **推論の飛び**: 「つまり〜」「ということは〜」の前後で、読者が補わないと繋がらない一段がないか
- 数字や比較の**指し先の曖昧さ**: 「6ms」「8〜10 分の 1」が本文・図・スクショのどの値を指すか読者に分かるか
- 読者が「それどうやったの？」と引っかかる**説明不足** (例: 有線 LAN の計測に使った機材)
- 変更箇所と前後の段落のつながり (差分赤入れのとき)
- 初出の固有名詞・製品名に一言の補足が要るか (要るかどうかは記事の想定読者で判断し、「好みで」と添える)

## 4. 通しでしか見つからない観点 (kind "pencil")

全文を頭から読むときに重視する。

- 章をまたいだ**表記ゆれ** (漢字/ひらがな、数字、三点リーダー等の記号の不揃い)
- 固有名詞・ゲームタイトル等の**表記が公式表記と揃っているか** (検索で引っかかる面も考える)
- 離れた場所での同語反復・近い言い回しの繰り返し
- 見出しと本文の整合、タイトルの問いに結びが答えているか、章の順序とつながり

## 5. 事実確認・公開前チェック

本文の主張とデータが噛み合っているかを実際に確かめる。読める画像は開いて見る。

- 本文の数字 (速度、倍率、価格、日付) と、スクショ・front matter・メタデータの整合
- 計算の検算 (「約 8 分の 1」は実際の数値で割って確かめる)
- **写り込み**: スクショに IP アドレス、ISP 名、氏名、メールアドレス、トークン、位置情報など公開すべきでない情報が写っていないか。
  写っていれば公開前に必ず直す指摘 (red) として出す
- 画像の alt テキストが空 (`![](...)`) または `Image` のような無意味な値になっていないか
- リンク先・引用元の記述が本文と一致しているか
- front matter (date、categories、draft) と本文の日付・内容の整合

## 6. 構成レビュー専用の観点 (kind "pencil")

一文一文の校閲はしない。記事全体のストーリーの通りを見る。

- タイトルは記事の結論・見どころと噛み合っているか (ズレがあれば方向性の違う代案を 2〜3 個。決めるのは筆者)
- 章立て・章の順序は妥当か。1 つの章に別の話題や時制が混ざっていないか
- 上から一度読んだだけで話が通るか。記事を「何の話」として読ませるかのフレームは立っているか
- 足すべき要素 (主張を支える実物・具体例・スクリーンショットの不足)、引くべき要素 (冗長な繰り返し、無くても通る段落)
- 結びはタイトルの問いに答えているか
- 件数は絞る。構成の指摘が 10 件を超えるならそれは焦点が定まっていない

原稿がまだ章立てされていない場合 (音声入力の書き起こしなど、見出しがほぼ無く話題が行ったり来たりする一枚岩のテキスト) は、
上記の代わりに「構成の立ち上げ」を行う:

- 原稿に含まれる話題を洗い出し、話題の切れ目と行き来を特定する
- 章立て案を 1 つ提示する (見出し案の列挙 + 各章に入る内容の一言説明)。記事全体への指摘 1 件にまとめる
- 各段落をどの章に収めるかの移動指示を出す。章ごとに 1 件にまとめてよい
- 同じ話題が離れた場所で繰り返されている箇所は、どちらに寄せるかを指摘する
- 提示するのは章立て案と移動指示まで。実際の並べ替え・見出しの記入・つなぎの文章は筆者が行う

## 7. 相談 (壁打ち) 専用の観点

筆者が自分でしっくりきていない箇所を指定してきたときの返し方。

- 原稿全体を読んで、該当箇所の文脈 (前後の流れ・記事全体での役割) をつかむ
- 診断: なぜしっくりこないのか、考えられる原因 (リズム・情報の順序・前後とのつながり・言葉のチョイス等) を
  筆者のメモも踏まえて具体的に
- 方向性の違う書き換え案を 2〜3 個。どれも筆者の語彙と文体 (だ・である調 + 口語崩し) を尊重し、ですます調にしない。
  案ごとに狙いの違いを一言添える
- 「今のままでも成立する」なら正直にそう言ってよい
- 採用するかどうか、どの案を選ぶかは筆者が決める

## 8. textlint 出力の扱い

リポジトリに .textlintrc* があれば `npx textlint --format json <原稿>` をかけ、出力をそのまま貼らずに吟味する。

- 本物の問題だけを指摘に翻訳する。ルールのメッセージの引き写しではなく、その文に即した具体的な修正案として書き起こし、
  末尾に (textlint: ruleId) と出どころを明記する
- kind は "red"
- 意図的な文体・レトリック (口語の差し込みへの ですます warning 等) と判断したものは指摘にしない
- textlint が実行できない場合はスキップして構わない (エラーにしない)
- GitHub Actions 上の @claude では textlint は使えない (workflow が許可していない)。試さずにスキップする。実行するのは akaire と手元の対話セッションだけ

## 9. 指摘の書き方

- **何が問題か → なぜ引っかかるか (読者にどう見えるか) → どう直すとよいか** の順で、短く
- 修正案は指摘の形で添える。文章を丸ごと書き直して渡さない
- 優先度が伝わるようにする: 文の成立・写り込みは red、構成・言い回しは pencil。好みの範囲のものはそう明記する
- 良かった点も伝える。筆者は人間であり、面白かった箇所・効いている構成はそう言われると次に活きる
